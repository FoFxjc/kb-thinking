# 06 · 架构决策记录

轻量 ADR：每条记录背景、决策与后果。状态：**已定** / **待定**。

---

### ADR-001 · Indexing Hub 只做编排，不做索引 — 已定

- **背景**：已有 Indexing API 负责解析、切块、向量化并写入 ES。
- **决策**：Hub 只负责变更发现、任务提交与追踪、溯源台账、统一管理。
- **后果**：Hub 轻量；溯源粒度受 Indexing API 能力约束（见 ADR-008）。

### ADR-002 · ES 是唯一的检索服务层 — 已定

- **背景**：ES 已在使用，Indexing API 直接写 ES。
- **决策**：MVP 不引入 Doris 或其他检索引擎；ES 同时承载溯源字段与 `concept_ids`。
- **后果**：检索能力受 ES 版本与 license 影响，需 Phase 0 确认。

### ADR-003 · MVP 不回写 Ozone，但必须可溯源 — 已定

- **决策**：处理结果不存回 Ozone；每个 chunk 记录 `source_uri`、版本 / 哈希、`job_id`、页码与位置。
- **后果**：溯源可靠性依赖 Ozone 对象版本保留；不可用时以 `content_hash` 检测失效。

### ADR-004 · 图谱是"概念图谱"，不是实例图谱 — 已定

- **决策**：只存金融投资概念、术语与关系，作为 Agent 的"顾问大脑"；不存具体公司、证券、持仓。
- **后果**：规模可控、以人工精选为主；适合用 Postgres 承载。

### ADR-005 · 概念图谱用 Postgres 普通表，不用 Neo4j / AGE — 已定

- **背景**：遍历深度 1–3 跳即可，规模在数千概念量级。
- **决策**：普通表 + 递归 CTE + `pg_trgm` 术语匹配。
- **后果**：零新增中间件；若将来需要 Cypher，可再加 Apache AGE。

### ADR-006 · 基础层人工精选，递增内容必须审核 — 已定

- **决策**：基础层由专家审核入库；从文档发现的新内容进入审核队列，永不自动覆盖基础层。
- **后果**：质量可控；需要明确的概念负责人。

### ADR-007 · Knowledge API 是唯一访问入口 — 已定

- **决策**：Portal 与 Agent（经 MCP）都只调用 Knowledge API；权限在此统一执行。
- **后果**：权限、审计、限流集中；Knowledge API 需高可用。

### ADR-008 · 概念标签的写回方式 — 待定

- **选项**：A. 经 Indexing API 的 metadata 更新接口；B. Hub 对 ES 直接局部更新。
- **取决于**：ES 写权限是否只开放给 Indexing API。

### ADR-009 · MVP 用户范围 — 待定

- **选项**：A. 仅内部投顾；B. 终端客户。
- **影响**：B 需要完整的适当性规则、话术审核与留痕，护栏重量级完全不同。建议 MVP 选 A。

### ADR-010 · MVP 不接入 Iceberg / Starburst — 已定

- **决策**：MVP 链路不经过湖仓；Hub DB、概念图谱、审计记录按可导出到 Iceberg 的方式设计。
- **后果**：MVP 更快落地；远期按 [07](07-target-architecture.md) 演进。
